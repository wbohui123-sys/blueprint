# 校准定稿（plan）

这一块要不要分？分成哪几个 part，每个交给 dock 还是 run，哪一批先上？

逐一回答以下问题

1. 这一块里有几个整体？好坏在彼此怎么配合上的一组东西，是一个整体；好坏各在自己身上、彼此只靠清楚的接口相连的，才是几个。
2. 几个整体之间的接口在哪？按接口切，切出来的每块能在台上单独看出好坏。
3. 每块交给谁？里面还有几个整体的派 dock，由它再分；一个整体的派 run，做到底；不值得派的自己做，用 subagent 帮手。
4. 这些工作量与协作节点中，哪些是核心工作（一切为这个服务），哪些是前置工作（必须提前做，影响后续全局），哪些是后续工作（整合、测试、反馈）
5. 哪些块要等别的东西先有，才撑得起来？
6. 所有节点工作需要的最小前置信息是什么？（这可能是我要准备的）
7. 怎么分效率最高？每样东西归谁，拆开的几块各要重学什么，最小的一版多快能碰到现实？答到换一种分法也省不下什么为止。

一个整体交给一个节点，几个整体才分开。一个 boss 的头雕、盔甲、斗篷和剑，一块表里咬合的齿轮，是一个整体：好在配合里，单独看每件都好，拼起来不一定好；配合只有一个脑子边做边调才调得出来，拆开就只能事先写成规格，各自照规格做到最好，规格错在哪没人看得见。表的机芯、表壳、表带，游戏的战斗、音频、场景，好坏各在自己身上、接口清楚，是几个整体。

分工一般应对几种情况
1. 需要多个不同领域专家级别的脑子协作（一个思维定势无法解决所有问题）
2. 工作量过大，分工来提速（比如多个工作量很大的模块分工行动）
3. 如果觉得无需分工，那就坚定地自己做就好。
4. 要么全自己做（自己做就不能分轮了），要么全靠分工（仅能准备必要context），分工完成你只负责整合递交测量误差，不继续修改

前两种只在几个整体之间成立。人拆，是因为一个人做不完、手艺各不相同；模型样样都会，能连着干很久，只为整体不同而拆，人类团队的分工只参考流程。一个整体再密再大，也交给一个 run，它在里面自己展开。扛不扛得下要算进去：系统自己的 run 上下文一长就伤质量。扛不下也不拆成零件并行，先宏观后细致：先做大形和方向，接进去看过，下一轮叫回它接着细化。

拆一次要付两笔：新节点从零开始，要重新读台、学流水线、搭验证，人学一次就记住，模型不会；每多一层，最小的一版碰到现实就晚一层。所以小步慢跑：先交出最小的一版，接进真东西看过，再往下铺。切出来只有一块、就是你手上这整块的，自己做，执行者写"无"；再派一个下级原样转手，只多一层。run 照 run 做到底，不往下派；接起来以后哪一块是大问题，下一轮再开新节点重做。

一轮派哪几个，看这一轮的台撑不撑得起它：动作要有真模型才验得了，镜头要有真场景，声音要对剪好的片子。它要的东西还没有，就先登记着，写明它依赖哪个 part，等交来了再派；硬派出去，它只能拿替身去猜，猜错了重做。

不读额外资料、不搜索、不测试；skill 可读。

答案交给谁：
- 职责写进节点文档。
- 用 node_doc.prediction（phase=plan）保存值得留下的认识。
- 向用户输出一段简要的问题讲述结论。

方案写成下面的分工表，用 next 交上来：handoff 写分工表全文；协作模式下用户先看，通过了这个环节才结束，接下来去执行。

方案里的做法可以随实践调整；请求、职责或已经记下的认识变了，重新定稿。

## 补充：任务边界与承接

- 判断整体看是否需要共同判断、能否分别验收；同一职位或模块里的多个独立问题不因此合成一个整体。耦合的整体保留一个责任节点，按上文先宏观后细致分轮推进；本轮请求说明这一小步的成果与范围，后续仍需完成的工作在任务表保留，不靠省略要求缩小任务。
- 每块的已有成果、尚缺输入和接入方写进现有分工表。只登记真实依赖；同一写入对象在同一轮由一个节点负责，无依赖且台已就绪的块同批派出。部分成果已够用时可先 publish，接收方仍遵守自己的正式前置。
