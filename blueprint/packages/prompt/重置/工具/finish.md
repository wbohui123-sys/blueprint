【正式交回】对照请求目的与本节点职责，交回实际结论；不通也是答案。Goal 状态不代表正式交回。交回的话派你的人要读，写短，不附证据长文。
result：achieved 做成了；unmet 没做成，或者关键的没验成。
handoff：做了什么、入口在哪、哪里没把握，几行就够。
checked：dock 和 run 必写，helm 不写：你怎么验的、验出了什么、证据在哪（写路径，不附长文）。怎么验由你自己定；没验成的照实写。
unchecked：没把握的、验不了的，一项一行，行首写给谁（「人：」或派你的节点）；没有就不写。
question：只给 run，可不填：要派你的节点定了才能往下做的事，一件一句。它定了以后，多半会把你叫回来接着做，这段对话里的东西都还在。
status：只给 helm：整页改写总图景，用户原话、要的效果、已定的取舍，下一件工作的 helm 最先读它。dock 这一块的现状写进成品里这一块的文档，不写这里。
lessons：可选，学到以后这个项目还会用的教训，一条一项（helm 记的是怎么分阶段、用户怎么问才答得好；dock 记的是怎么切 part、台怎么搭）：title 一句话写什么情境用得上；situation 情境；reflex 看起来对、其实会错的做法；instead 应该怎么做；because 哪次碰到了什么。没有就不填。
ask_user：你是 helm、这一阶段是 build 时必填；执行节点可选，问方向或请用户协助验收。写法同 next：没有要问用户的写"不用"；有，先在正文里问，这里写那一个问题，系统停下等用户回话，这次不交回。
files：交出去要看的相关文件：成品的入口、要读的文档，写路径，一项一个；没有就不填。交回后它们和你交回前对用户说的那段话一起出现在对话里，点开就能看。
parts：你交出的东西，一样一行，记进整合表，派你的节点整合时照它一样样接。what 写是什么；work 做了写 done，没做写 todo（要别人接着做的事也写成一行，reason 写要谁做什么），不做写 dropped；where 写在哪看得到它（交付里的入口、预览）；effect 写量到的效果；好不好要人看的，judge 写 human。重交表上已有的那一样，写它的 id（比如 1.2#3）。要接的、要别人做的写在这里；没把握、验不了的照旧写 unchecked。

交回前，你的实际子节点都须收束。交回时系统自动提交你的改动、并进派你的节点的分支、写好总图景和经验、通知派你的人；并进时撞上冲突，这次交回不成立，结果里列出冲突，你解决后再交回。正式交回当前承接的全部责任；直接孩子全部交回再统一通知母节点。还欠着的求助不会自动回掉，交回以后系统照样叫醒你去回。重复交回复用已有记录。

## 补充：带着已有结论交回

- checked 用最短的说明标明验了什么、结果、适用的产物版本与证据入口；已有日志、CI 结果或最终 verification 收据均可引用，不要求另做一份证明或为生成收据重跑。正在运行的作业和未验证项不能写成通过。
- 后续工作沿用 parts 的 todo／reason 说明需要谁接什么，派出者据此在任务表安排；留下待办不解除本节点当前承接的责任。交回时带上已确认适用的局部验证结论与剩余接缝，接手者无需从头摸底。
