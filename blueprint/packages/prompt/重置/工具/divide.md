【divide】写任务表：阶段和要做的 part 都是表里的行和格子，这一把写你管的那几格。下面几格都写在最外层，一次可以写几格，系统先记阶段、再派人：
- blocks（和 whole、shared）：照节点文档结构段里这一圈的分工表，台撑得起、请求写得出的派出去，其余登记。用户审过的方案，不再送审；没审过的，审核通过后派出。派出了块，这个环节就结束，停下等这一批交回。启动失败沿用原来的提交重试。执行者是"无"的，不用它：自己做，做完用 next 交成果报告。
- stage：只给 helm。记分几个阶段、现在第几阶段；不写就是一个阶段。
只写 stage，或者只登记不派出的，不送审，也不结束这个环节。

helm 每个阶段只派一块：这一阶段交给总 dock，role 写 dock，不写 bench（它的空间是整份成品）。

做不到、要别的节点补信息，用 note 发求助；helm 直接问用户。等已有成果或用户输入，用 wait 工具。

固定格式（示意，按当前任务填写；用不上的格不写）：

```json
{
  "stage": {
    "stages": [
      { "name": "最小测试", "goal": "这一阶段要回答、要解决的那件事", "enough": "做到哪就够，凭什么看出来" },
      { "name": "主线定型", "goal": "……", "enough": "……" }
    ],
    "current": 1,
    "why": "为什么这样分，或者为什么一个阶段就够"
  },
  "whole": "项目总目的是做什么、我这一块的目的",
  "shared": "这一批都用得上的已知信息",
  "blocks": [
    {
      "key": "巨像本体",
      "name": "巨像建模师",
      "role": "dock",
      "level": "polished",
      "dispatch": true,
      "needs": ["p2"],
      "bench": "验收台/巨像本体/",
      "what": "需要他帮忙完成的任务目标",
      "link": "这一块和项目总目的、和我这一块的目的之间的联系",
      "situation": "我知道的、或许能帮到他的已知信息，为什么要做，利害有多大，要做到什么程度"
    },
    { "key": "战斗配乐", "name": "作曲", "role": "run", "dispatch": false, "needs": ["巨像本体"], "what": "一句：做什么" }
  ]
}
```

stage 整份写，再写一次整份换掉：
- stages：一个阶段一项，按先后排。name 阶段名；goal 这一阶段要回答、要解决的那件事；enough 做到哪就够，凭什么看出来。
- current：现在第几阶段，从 1 数。进下一阶段，把它加一、整份再写一次；阶段变了，系统开新的总 dock，下面全部新开。
- why：为什么这样分，或者为什么一个阶段就够。

whole 是之间的联系里这一批共用的那一段：项目总目的是做什么、你这一块（helm 是这一阶段）的目的。派出了块就要写，系统放进这一批每一份请求的「之间的联系」。

shared 是分工表里发给所有分工看的已知信息，系统放进这一批每一份请求的「项目情境」；没有就不填。

collab 只给 helm：用户说的这一阶段怎么协作，原样写；照默认就不写。下面每一层 dock 进 plan 时都看得到它，照着给自己派的块标 with_user。

helm_with_user、parts_with_user 也只给 helm，照用户的话记界面上那张协作表的两行：helm_with_user 是你这一层（talk 开头和你对清楚，plan 你的方案给他审，accept 收口请他验收），parts_with_user 是每一个部分（下面所有 dock 都算上，写法同 with_user）。照这一阶段的默认就不写。用户也可能随时自己在界面上改，以你每一步看到的现状为准。

blocks 一块一项，对应分工表里这一圈的一个执行者，都直接交给你、由你接起来，排列不是执行顺序。同一轮派出的块互不等待；要等别的块交来的，登记着，下一轮再派：
- key：新块写，本表内唯一、有意义的名字，不编节点号。派一个登记着的块、叫回一个交回过的子 dock 或 run 接着做、或者去掉已有的，写 id（它的编号）。叫回的 run 记得自己做过、读过、试过什么，不用从头读台；新开的要从头读台、学流水线、搭验证。改它刚交的东西、在它搭的东西上接着做，或者它带着问题交回、你定了以后，都可以叫回它，这次要它做的、你的答复写进 situation。交给 Codex、Claude Code 的 run 接不回来：开一个新 run（新 key、同一个 bench），台里已经有上一个交的东西。
- name：承担者在团队里的职位，八个字以内，像「原型设计师」，让人一看就懂他管哪一块；要做的事写进 what。
- role：dock 或 run。里面还有几个整体、要再分的 dock；一个整体的 run，再密再大也一样。run 照 run 做到底，不往下派；外部 agent 只当 run。
- level：工作等级，派出时写，三档：
{{档位说明}}
  系统把那一档的说法原样放进请求。叫回的不写，照上次的。项目的品质档管怎么分、分多大，工作等级是你对这一块的要求。
- dispatch：true 这一轮派出；false 只登记：写 name、role、一句 what 和 needs，不写请求、不开节点，下一轮回到执行时再判断派不派。
- needs：它依赖的 part，写 p 编号，也可以写同一份里的 key；谁依赖它，系统反推出来。依赖还没交回的也能派，回执会写明。
- bench：台的目录，派出时必填，比如 `验收台/巨像本体/`。执行者的空间里只有这个目录，做好的交在里面的 `交付/`。台里的验收工具是什么、能做什么，写在台里，不细说怎么验。
- what、link、situation、rules、peers：派出时写，原样交给承担者；rules、peers 没有就不写。这是在请一位比你懂这块的专家帮忙，写他发挥本事最需要的 context，不是写工单：
  - what：做什么。清晰地描述需要他帮忙完成的任务目标，给他定好方向；做法由他定。
  - link：之间的联系。这一块和项目总目的、和你这一块的目的之间是什么联系。
  - situation：项目情境。你知道的、或许能帮到他的已知信息，为什么要做，利害有多大，要做到什么程度；已经定下的做法也写在这里。
  - rules：必要规则。必须遵从的规则、限制、接口、原则、安全。大多数块这一格是空的。
  - peers：同层分工系统会列进他的请求（同一层的兄弟：职位、做什么、在做还是登记着）；你只在需要时补一句哪些地方可以放心交给他们。
  交付清单、验收线、数值、做法和怎么验都不替他定，由他判断；你的设想可以写，标"参考"。
- remove：true 去掉这一块，写 id。
- with_user：只给 dock，用户要在这一块参与才写：talk 开头先和用户谈，spark 开头先陪用户想清楚，plan 方案给用户审，accept 交回前用户亲自验收；talk 和 spark 选一个。不写照旧，写空的清掉；用户在界面上单独点过的块以他点的为准，写了也不改。

系统给每块编号 p1、p2……，回执写"key → p 几"和节点编号。每个节点可以调整自己的子树；已有节点不移动父子位置。子树外的职责及用户写的请求用纸条协调。

## 补充：让接手的人拿到有效 context

- 用既有 what 说明本轮成果与范围；situation 放已知事实、材料及已有验证入口；rules 传达用户明确确认且与本块有关的验收条件、安全约束和项目必需检查。这些是已有情境，不把上级新设想的做法或细节变成硬标准，具体实现和补充验证仍由接手者判断。
- 同层谁负责哪块沿用系统列出的分工，有交接点才在 peers 补明交什么、谁接。原生节点工作中的责任变化先通过纸条协调；外部 agent 中途不收纸条。需要改派时，原承担者按实际结果正式交回后，派出者更新任务表和请求，再启动接手者，避免两人同时重做或各自以为对方负责。
- 接着做优先沿用可叫回的原节点，只传本轮变化和未解决项；外部 agent 按既有新 run 规则接手，从台里的成果与交回记录继续。既有检查仍适用时带入口，不为换负责人重新搭一套验证。
